> 本文件优先级高于 PRD 中的技术描述。所有开发动作（含 AI 自动开发）必须遵守本文件。
> 修改本文件必须经产品方确认；技术栈中途不得随意变更。

### 1.2 单文件行数红线

1. **任何手写文件不超过 500 行**，目标控制在 300 行以内。
2. 代码超过限制时，按职责拆分文件，不得机械截断：
   - Vue 组件拆成“容器 + 子组件 + composable”；
   - 纯逻辑拆成多个模块；
   - 内容数据按 `docs/数据规范.md` 第 7 节拆分，**不适用本行数限制**。
3. 例外（仅限自动生成文件）：`package-lock.json`、`dist/` 构建产物、代码生成器输出；例外文件必须在头部注释标明“自动生成，勿手改”。
4. 内容 YAML 属于数据文件，单文件建议不超过 1000 行，具体拆分规则见 `docs/数据规范.md`。
5. 修改任何文件前先确认目标文件行数，避免把文件越改越大。

### 1.3 模块职责（开发后以此为准）

| 模块 | 职责 | 禁止事项 |
|---|---|---|
| `domain/` | 记忆调度、出题规则、方药关系、检索索引 | 不 import Vue、不操作 DOM |
| `data/` | 读取 content、运行构建期校验、提供类型化数据 | 不写业务逻辑 |
| `store/` | IndexedDB 读写、状态持久化、备份导入导出 | 不直接写界面 |
| `ui/` | 页面与交互 | 不内嵌大段业务算法 |
| `content/` | 纯数据 | 不写代码 |
| `scripts/` | 校验与构建工具 | 不参与运行时 |

## 3. 技术偏好

1. **函数式优先**：核心逻辑写成纯函数，输入输出显式，不依赖全局状态；非必要不写 class。
2. **少引依赖**：能用原生 API（Date、Intl、Web Speech、crypto 等）就不引库。
3. **状态管理从简**：不引入 Pinia/Vuex；用 composables + Dexie 持久化，状态模块化在 `store/`。
4. **类型安全**：TypeScript `strict: true`；业务数据必须有显式类型或 schema；禁止无说明的 `any`。
5. **数据不可变**：复习调度、出题等核心计算不原地修改输入数据。
6. **错误要可见**：内容数据校验失败必须给出具体文件、字段和修正建议，不允许静默跳过。
7. **兼容移动端**：界面以手机宽度优先开发，再适配桌面。

## 4. 命名、注释与代码风格

### 4.1 命名

| 对象 | 规则 | 示例 |
|---|---|---|
| 目录 | kebab-case | `domain/memory/` |
| Vue 组件 | PascalCase.vue | `ClauseCard.vue` |
| 页面组件 | 名词 + View.vue | `ClauseDetailView.vue` |
| 组合式函数 | use + PascalCase/camelCase | `useDailyTask.ts` |
| 普通 TS 文件 | camelCase.ts | `scheduler.ts` |
| 测试文件 | 同名 + .spec.ts | `scheduler.spec.ts` |
| 类型/接口 | PascalCase | `ClauseContent` |
| 常量 | UPPER_SNAKE_CASE | `DEFAULT_NEW_PER_DAY` |
| 内容数据文件 | kebab-case，按篇章 | `taiyang-shang.yaml` |

### 4.2 注释

- 注释使用中文。
- 导出的函数/类型必须有 JSDoc：用途、参数、返回值、副作用。
- 只写“为什么”的注释，不写“做了什么”的废话注释。
- 临时方案用 `TODO(负责人): 说明`，提交前尽量清零。

### 4.3 代码格式

- 统一使用 Prettier 格式化：2 空格缩进、单引号、无分号、行宽 100、换行符 LF。
- ESLint 规则以 Vue 3 + TypeScript 推荐配置为基础，`strict` 开启。
- 项目提供 `npm run format`、`npm run lint`、`npm run typecheck`、`npm run test`。
- **每次提交前必须通过 format + lint + typecheck + test，否则不得提交。**
- `.editorconfig` 已提交，IDE 配置与 Prettier 保持一致。

## 5. 开发服务与热更新

1. 开发使用 Vite：`npm run dev`。
2. Vite 自带热更新（HMR），**改页面、组件、样式、内容数据后禁止重启服务**；刷新浏览器或等待热更新即可。
3. 只有以下情况才允许重启：修改 `package.json`、安装/卸载依赖、修改 `vite.config.*`、Tailwind/PostCSS 配置、`tsconfig` 结构变化。
4. 需要重启时必须先说明原因，并只重启一次。
5. AI 启动服务后保持其在后台运行；判断服务是否正常用浏览器/HTTP 检查，而不是反复重启。
6. PWA 离线缓存只在生产构建中验证；开发模式不把缓存问题误判为服务问题。

## 6. Git 版本管理

### 6.1 基本要求

1. 项目必须使用 Git 管理；仓库根目录为项目根目录，默认分支使用 `main`（若初始化为 `master`，在首次提交前执行 `git branch -m main`）。
2. 提交采用 Conventional Commits，中文描述，格式：
   `type(scope): 简述`
   - type：`feat` / `fix` / `docs` / `refactor` / `test` / `chore` / `content`
   - scope 示例：`content`、`memory`、`search`、`ui`、`store`、`infra`
3. **每完成一个可独立验证的小部分就提交一次**，例如：
   - 完成某一篇条文数据 → `content(shanghanlun): 新增太阳病上篇条文数据`
   - 完成每日任务逻辑 → `feat(memory): 实现每日任务队列与FSRS调度`
4. 提交前跑完整检查；提交粒度小、可回退，禁止“攒一大坨再提交”。
5. 根目录 `.gitignore` 已提供；`node_modules/`、`dist/`、日志、本地环境文件不得入库。
6. 不使用 `git push --force`；不直接改写已共享的历史。
7. 云端仓库（GitHub/Gitee）等产品方提供地址后再关联推送；未关联前也必须保证本地持续提交。
8. 每个阶段完成后打 tag，例如 `v0.1-mvp`。

### 6.2 AI 协作提交规则

- 每个任务开始时先 `git status`，确认工作区干净。
- 任务完成并验证后立即提交，提交信息须说明“改了什么、为什么”。
- 一次提交只包含一个任务的改动，不夹带无关修改。
- 发现上一步有隐患时，先单独提交修复，再继续新任务。

## 7. 内容数据规范

1. 字段级规范以 `docs/数据规范.md` 为准；本文档只保留目录与提交层面的约定。
2. `content/` 下每本书一个目录；书内按“版本 → 篇 → 条文”组织。
3. 条文 ID 稳定且全局唯一：`书代码.版本代码.篇章代码.条文号`（如 `SHL.SB.TYS.001`）；发布后不得更改。
4. 内容文件拆分规则见 `docs/数据规范.md` 第 7 节：内容 YAML 不适用 500 行限制，单文件建议不超过 1000 行，超限按“篇 + 段”拆分。
5. 内容修改与代码修改分开提交。
6. 所有内容在构建期自动校验：缺译文、缺注解、方药关系断裂、ID 重复等必须构建失败，校验规则见 `docs/数据规范.md` 第 6 节。
7. 内容来源与版权信息写在数据文件头部注释中；公版与自编内容分开标注。

1. PRD、项目计划、项目地图、数据规范、学习计划与统计口径、核心模块设计、用户协议、工程初始化方案、内容录入与校对流程、测试计划、内容校验脚本规格、本规范、需求变更记录都放 `docs/`。

3. 视觉设计稿由产品方放入 `design/`，开发前同步到 PRD 第 11 节。
4. 本文档自身也要遵守 500 行限制，超限时按主题拆分。
