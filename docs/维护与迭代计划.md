# 维护与迭代计划（AI 协助执行版）

> 版本：v0.5　|　2026-08-19
> 适用范围：灵素 v0.1 至后续所有版本
> 执行方式：**日常维护与迭代由 AI 按本文件执行，产品方（人）负责方向拍板、外部事项与验收。**
> 配套文档：`docs/PRD.md`（§9 版本规划）、`docs/项目计划.md`、`docs/MVP验收清单.md`、`docs/测试计划.md`、`docs/开发规范.md`、`docs/项目地图.md`、`docs/内容录入与校对流程.md`
> 维护原则：每次会话结束时工作区干净、验证全绿、文档已同步；AI 不得在没有测试的情况下改行为（TDD）。

---

## 1. AI 维护会话标准流程

每次维护会话按以下流程执行（AI 主动执行，不需要人逐步指挥）：

1. `git status` + `git log -5`：了解当前工作区与最近进展；
2. 阅读本文件第 2、4 节，选出一个**最高优先级、无外部阻塞**的任务；有歧义时向产品方确认，不自行扩大范围；
3. 阅读该任务对应的规范文档（PRD / 核心模块设计 / 设计规范 / 数据规范）；
4. 跑基线：`npm run test`、`lint`、`typecheck`、`validate:content`，确认开工前全绿；
5. 按 **TDD** 完成：先写失败测试 → 看它失败 → 最小实现 → 全量测试通过 → 需要时重构；
6. 全量验证：test / lint / typecheck / validate:content / build；
7. 同步文档（见 §9 文档同步清单），更新本文件中的任务状态与季度复盘；
8. 按 Conventional Commits 提交，一个任务一个 commit。

**会话完成定义**：工作区干净、五项验证全绿、文档与代码一致、有 commit。

## 3. 维护节奏表

### 3.1 每次维护会话（AI）

见 §1 标准流程。最低要求：**基线全绿 → 改 → 全量验证 → 同步文档 → 提交**。

### 3.2 每周（AI，约 15 分钟）

1. `git log --oneline -10` 回顾本周改动；
2. `npm audit` 查看新漏洞（如有高危，当周修复）；
3. 检查 `content/shanghanlun/校对记录.md` 是否有未闭环的用户反馈纠错问题；
4. 检查 Issues（bug / 内容纠错 / 功能建议三类模板），能修的登记到本文件；
5. 更新本文件任务状态与 `docs/MVP验收清单.md`。

### 3.3 每月（AI + 人确认）

1. 备份演练：导出 JSON → 清空 IndexedDB → 导入 → 核对学习进度完整（人操作，AI 给步骤）；
2. 依赖审查：`npm outdated`，需要升级的登记 `docs/开发规范.md` 依赖表后升级；
3. `CHANGELOG.md` 补充本月变更；
4. 检查 PWA 缓存配置与构建体积（`npm run build` 输出），记录到技术债台账。

### 3.4 每季度（AI 出报告，人决策）

1. **覆盖率**：`vitest --coverage`，core domain/store 低于 90% 则补测试；
2. **依赖主版本评估**：逐一评估升级收益与风险，人拍板是否升级；
3. **性能体检**：build 产物体积、首屏加载、搜索索引构建耗时，对照技术债台账；
4. **技术债评审**：逐条过 §4，该还的还、该关闭的关闭；
5. **路线图评审**：对照 §2 与 PRD §9，按用户反馈调整优先级；
6. 填写 §8 季度复盘记录。

### 3.5 每次发布（人 + AI）

执行 §5 发布检查单，全部通过才允许发布。

卡片式管理；还债时先写失败测试（如适用）再改，完成后更新状态。

| 编号 | 现状 | 影响 | 修复方案 | 工作量 | 验收标准 | 状态 |
|---|---|---|---|---|---|---|
| TD-1 | `echarts` 在依赖中但代码未使用 | 依赖冗余、安全隐患面 | 阶段 0 从依赖移除；若 E-7 提前做则改为按需引入 | 0.5h | `npm ls echarts` 为空，build 无相关告警 | ⏳ |
| TD-2 | `content.json` 477KB 全量加载（build chunk>500kB 警告来源） | 首屏慢、内存高，M2 内容翻倍后更严重 | 按篇拆分 JSON + 路由级懒加载（T1-6/E-9） | 4–8h | 首屏只载当前篇，单 chunk 体积下降，测试通过 | ⏳ |
| TD-3 | 字号三档设置已存 DB，但阅读页未应用 | 设置项形同虚设 | 阅读页（条文/方剂/注解）按 `fontSize` 设置映射字号 | 2h | 三档切换原文字号实时变化，有组件测试 | ⏳ |
| TD-4 | 无测试覆盖率门禁 | 无法量化质量、回归保障弱 | 引入 `@vitest/coverage-v8`；CI 加 coverage 步骤 | 2h | 覆盖率报告生成，domain/store ≥90%，CI 不过即红 | ⏳ |
| TD-5 | 无 E2E 冒烟测试 | 关键链路只靠组件测试，真机回归成本高 | Playwright 三条链路：协议→背诵 / 搜索→条文 / 刷题→错题本 | 6–8h | CI 或发布前可一键跑通 | ⏳ |
| TD-6 | 搜索索引在页面 `onMounted` 同步构建（`核心模块设计.md` §5.3 原计划 Web Worker） | 内容翻倍后可能卡顿 | M2 前实测构建耗时，超阈值则迁 Worker；否则文档登记"维持同步实现" | 先评估 | 决策记录 + 如迁移则有测试 | ⏳ |
| TD-7 | 托管环境安全头（CSP 等）未配置 | 上线后安全风险 | 部署时按托管平台配置 CSP / 缓存头 | 1h | 线上响应头检查通过 | ⏳ |
